Source: `claude/charming-rubin-pi8nzs` commit `cccd0b4`. Spec: `docs/08_exp09_every_step.md`.
Priority: after exp05 (unary + binary) and the Life ensemble, which are still pending on your side;
nothing from them has reached GitHub as of 20:00 UTC. Please post status on those first.

## Finding that motivates it
The step budget is a function axis. `u1map budgets --every 8` on 2,097,152 champion programs: 5,982
distinct functions at T = 256, 98,445 across 32 checkpoints (16.5x), every checkpoint adding 2,700-3,900
functions seen at no other T. The `x*3` program (0x521) is `10x` at T = 248 and `9x` at T = 240. Snapshots
verified equal to the sweep at T = 256 on two ISAs.

## What to run (champion ISA `SWAP,ADD,NAND,SKZ`, W=4 a=2 p=3 I=4)
1. Kernel variant of `gpu/u1_cuda.cu` / `gpu/u1.comp`: run 256 steps once per program, hash the truth
   table at every checkpoint into one hash table per checkpoint; skip hashing when the table equals the
   previous checkpoint's. 32 checkpoints per pass (unary: 32 x 84 MB tables), 8 passes = all 256 steps,
   ~10 min total on the 9 GPUs. Shard v2 record = {key_lo, key_hi, program u32, T u16}; header magic
   0x55314232.
2. Validate each pass on programs [0, 2^20) at T = 8, 100, 256 against the CPU reference:
   `mapper/target/release/u1map budgets --W 4 --a 2 --p 3 --isa SWAP,ADD,NAND,SKZ --lo 0 --hi 1048576 --every 1`
   (per-T distinct counts must match; for a byte-exact check compare the per-T key sets).
3. Binary mode: every 8th T first (4 passes x 8 tables x ~7 min = ~30 min). Every step only if the unary
   growth curve justifies it (32 passes, ~4 h, ~150 GB per-T data: falke64's disk).
4. Publish shard v2 archives like the exp03 witnesses; post |F(T)| per T, pass wall times per GPU model.

## Data volume (from the spec)
Unary: per-T maps 5.5 GB, union 0.5-2.5 GB (30-150 M functions estimated). Binary: per-T every 8th
19 GB, union 8-50 GB. Raw tables (8.8 TB unary) are never stored.

## Fable does in parallel
Shard v2 reader, `u1map build --multi` (union map with minT, abundance, T-histogram), `catalog --deep`
and `usability.py` with minT as the cost column, the catalog of the union, and the write-up. So the
kernel's record format is the only interface we must agree on: {key_lo u64, key_hi u64, program u32,
T u16}, little-endian, header as in v1 plus the new magic. Say so here if you need a different layout.
